    # 退货资格判断

    按顺序检查，任何一步不通过就停下，把不通过的那一条讲给客户：

    1. `create_return` 只对 `status == delivered` 生效，其余状态先解释当前进度
    2. 查该品类的 `return_window_days`，用 `days_since_delivery` 比较（等于窗口当天仍然可以）
    3. 数码品类 `activated == true` 时，无理由退货不成立
    4. 窗口为 0 的品类（食品）不支持无理由退货
    5. 质量问题、发错货、少件漏发不受窗口限制，也不受第 3 条激活限制，且运费由平台承担

    ## 先判断资格，再判断要不要开单

    第 1~5 步是**资格判断**，它只回答"能不能退"，不回答"现在要不要开单"。
    资格通过不等于立刻开单——开单还要看客户有没有明确要求办理，以及信息是否齐全。

    - **资格不通过**（超窗口、激活、品类不支持等）→ 停下，说明原因和替代方案，
      **不要调用 `create_return`**。客户说"想退"也不能开，政策是硬边界。
    - **资格通过但客户只是在问**（"能退吗""来得及吗"）→ 说明政策并问要不要办。
    - **资格通过且客户已表达办理意愿**（"想退""要退""帮我退""一起退"）→ 直接调用
      `create_return`，开完单再告诉客户运费和后续。
    - **资格通过但关键信息缺失**（订单号没给、要退哪件商品不明确、退货原因不明）→
      先追问补齐，**不要猜、不要替客户选一个原因就开单**。

    多个商品时逐个走这套流程，能退且客户已要求的当场开单，不要攒到最后一起问。

    ## lookup_order

    只接受完整的订单号（形如 AB12345678）。没有按客户名、手机号、商品模糊搜索的能力，
    所以客户没给单号时**只能反问**，不要在参数里塞占位符。

    返回里要看三个字段：

    - `status`：只有 `delivered` 才能发起退货；`shipped` 引导客户拒收；`refunding`/`refunded` 说明已在流程内
    - `days_since_delivery`：从签收日算起的天数，退货窗口用它判断
    - `activated`：数码品类里这一项为 `true` 表示已激活

    ## get_return_policy

    按品类查窗口天数和是否支持无理由退货。不同品类窗口不同（家居 15 天，服饰/鞋靴/数码 7 天，
    食品不支持），**不要用统一天数回答**。质量问题的退货运费由平台承担，无理由退货由客户承担 12 元。

    ## 查完之后：先对窗口，再决定动作

    拿到 `days_since_delivery` 和 `return_window_days` 后，**先做一次比较**：

    - `days_since_delivery > return_window_days` 且客户没有主张质量问题/发错货/少件漏发
      → 已超无理由退货窗口，**不能调用 `create_return`**。告诉客户超期了、说明原因，
      并给出替代方案（如转人工评估）。客户说"想退"也不改变这个结论。
    - 在窗口内 → 再按客户是"询问"还是"要求"决定是说明政策还是直接开单。

    ## 开单前必须齐的三样

    调用 `create_return` 之前确认：订单号（客户给的或已查到的）、要退的商品、
    退货原因（无理由 / 质量问题 / 发错货 / 少件漏发）。缺任何一样先追问，
    **不要默认按"七天无理由"替客户填原因**。
